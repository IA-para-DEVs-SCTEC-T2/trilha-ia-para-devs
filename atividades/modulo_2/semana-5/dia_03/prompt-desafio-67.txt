==================================================
OBJETIVO DO EXEMPLO
==================================================

Criar um agente LangGraph para o case:

Um cliente pede cancelamento de pedido ou reembolso em uma loja online.

O agente pode:
1. carregar os dados do cliente;
2. interpretar a intenção do usuário;
3. avaliar se há prompt injection;
4. classificar o risco;
5. aplicar política de autorização;
6. decidir a rota;
7. executar a tool, bloquear ou solicitar aprovação humana;
8. gerar resposta final.

Mensagem principal para os alunos:

A LLM pode interpretar e gerar resposta, mas a execução da tool passa por regras, política e aprovação humana.

==================================================
BASE MOCKADA
==================================================

Use uma base simples:

CLIENTES = {
    "123": {"cliente_nome": "Mariana Lima", "role_usuario": "cliente"},
    "456": {"cliente_nome": "Neymar Jr", "role_usuario": "cliente"},
    "789": {"cliente_nome": "Anitta", "role_usuario": "atendente"},
    "999": {"cliente_nome": "Taylor Swift", "role_usuario": "gerente"}
}

PEDIDOS = {
    "45821": {"pedido_id": "45821", "cliente_id": "123", "status": "em transporte", "valor": 249.90},
    "77710": {"pedido_id": "77710", "cliente_id": "456", "status": "aguardando pagamento", "valor": 899.90},
    "88001": {"pedido_id": "88001", "cliente_id": "789", "status": "entregue", "valor": 129.90},
    "99002": {"pedido_id": "99002", "cliente_id": "999", "status": "em separação", "valor": 1599.90}
}

==================================================
TOOLS MOCKADAS
==================================================

Criar tools simples:

- consultar_pedido(pedido_id)
- cancelar_pedido(pedido_id)
- reembolsar_pedido(pedido_id)

As tools devem retornar dicionários simples.

Exemplo:

{
    "status": "sucesso",
    "mensagem": "Pedido 99002 cancelado com sucesso."
}

==================================================
STATE DO LANGGRAPH
==================================================

Criar um TypedDict chamado AtendimentoState com os campos:

- mensagem_usuario: str
- cliente_id: str
- cliente_nome: str
- role_usuario: str
- intent: str
- pedido_id: str | None
- injection_detectada: bool
- risco: str
- decisao: str
- motivo: str
- aprovacao_humana: bool | None
- tool_result: dict | None
- resposta_final: str
- caminho_executado: list[str]

==================================================
NODES OBRIGATÓRIOS
==================================================

Criar os seguintes nodes:

1. carregar_cliente

Busca cliente_nome e role_usuario a partir de CLIENTES[cliente_id].

Importante:
A role do usuário vem da base mockada, não da mensagem do usuário.

2. interpretar_intencao

Detecta intent e pedido_id.

Pode ser simples, usando regras por palavras-chave:

- se tiver "status" ou "consultar" -> consultar_pedido
- se tiver "cancel" -> cancelar_pedido
- se tiver "reembolso" ou "reembols" -> reembolsar_pedido
- caso contrário -> desconhecida

Extrair pedido_id com regex.

3. avaliar_seguranca

Detecta prompt injection simples.

Se a mensagem tiver termos como:
- ignore instruções
- delete
- token
- senha
- segredo
- bypass

Então:
injection_detectada = True

4. validar_risco

Classifica risco:

- consultar_pedido -> baixo
- cancelar_pedido -> alto
- reembolsar_pedido -> alto
- desconhecida -> medio
- injection_detectada=True -> critico

5. aplicar_politica

Aplicar regras:

- Se injection_detectada=True -> decisao = bloquear
- consultar_pedido -> permitir
- cancelar_pedido -> só gerente pode solicitar; exige aprovação humana
- reembolsar_pedido -> só gerente pode solicitar; exige aprovação humana
- cliente tentando cancelar ou reembolsar -> bloquear
- intent desconhecida -> bloquear

Retornar:
- decisao: permitir | pedir_aprovacao | bloquear
- motivo

6. solicitar_aprovacao

Não executa tool.

Retorna resposta dizendo que a ação exige aprovação humana.

7. executar_tool

Executa apenas se:
- decisao == permitir
ou
- decisao == pedir_aprovacao e aprovacao_humana == True

Se aprovacao_humana for False ou None, não executar.

8. bloquear

Não executa tool.

Preenche resposta final com motivo do bloqueio.

9. gerar_resposta

Gera resposta final com base no que aconteceu.

Pode ser determinístico, simples e claro.

==================================================
ROTEAMENTO
==================================================

Criar função:

decidir_rota(state)

Regras:

- se state["decisao"] == "bloquear" -> "bloquear"
- se state["decisao"] == "permitir" -> "executar_tool"
- se state["decisao"] == "pedir_aprovacao" e state["aprovacao_humana"] is True -> "executar_tool"
- se state["decisao"] == "pedir_aprovacao" e state["aprovacao_humana"] is False -> "bloquear"
- se state["decisao"] == "pedir_aprovacao" e state["aprovacao_humana"] is None -> "solicitar_aprovacao"

==================================================
GRAFO
==================================================

Montar o LangGraph com esta sequência:

START
-> carregar_cliente
-> interpretar_intencao
-> avaliar_seguranca
-> validar_risco
-> aplicar_politica
-> rota condicional:
   - executar_tool
   - solicitar_aprovacao
   - bloquear
-> gerar_resposta
-> END
